# Evaluation Plan: Learned EHR Representations vs. Heuristic Baselines

## Overview

We evaluate whether **learned context selection improves downstream LLM QA performance** compared to standard retrieval heuristics. The core experiment is a **model × retrieval method** matrix: for each combination of frozen downstream LLM and retrieval strategy, we measure answer quality on the same set of clinical questions.

The independent variable is the **context selection strategy**. The downstream LLM is always frozen — we never fine-tune it. Any improvement in answer quality is attributable to the retrieval layer selecting better evidence.

---

## Input Data

**Patient timelines** (`data/processed/patient_timelines.json`) — each record contains:
- `discharge_summary` — full text of the discharge note
- `events` — temporally sorted structured clinical events (labs, vitals, meds, procedures, diagnoses)
- `demographics` / `admission` — patient and encounter metadata

**QA pairs** — two sources:
- `data/generated/qa_pairs.json` — generated by gpt-4o via the Generation pipeline. Each entry contains 5 QA pairs per admission with `question`, `answer`, `difficulty`, `source_types`, and `reasoning` fields.
- `data/physionet.org/files/ehr-ds-qa/1.0.0/mimic_iv_note_qa.json` — EHR-DS-QA dataset (~156k QA pairs, ~500 physician-verified). Generated from discharge summaries only.

QA pairs are joined to timelines at evaluation time by matching on `(subject_id, hadm_id)`.

---

## Retrieval Strategies (columns of the matrix)

Every strategy starts from the same patient record. The only difference is **which chunks are selected** for the LLM's context window.

### Baseline 1: Discharge Summary Only

Feed the full discharge summary text + question to the LLM. No structured data, no retrieval. Represents current clinical practice.

**Context**: `discharge_summary`

### Baseline 2: Full Context (Everything)

Serialize all available data — demographics, admission, all events, discharge summary — into a single text prompt. Tests whether more information helps or hurts (context overload).

**Context**: `demographics` + `admission` + `events` (all) + `discharge_summary`

### Baseline 3: Recency-Based Filtering

Include only the N most recent events (by timestamp) before discharge, plus the discharge summary. Tests a simple temporal heuristic.

**Context**: `discharge_summary` + last N events (vary N = 10, 25, 50, 100)

### Baseline 4: BM25 Retrieval

Chunk the patient record (discharge summary + serialized structured events) and retrieve the top-k chunks by BM25 keyword matching against the question. Classic information retrieval baseline.

**Context**: top-k chunks by BM25 score (vary k = 3, 5, 10)

### Baseline 5: Semantic Similarity Retrieval (Traditional RAG)

Embed each chunk using a sentence-transformer model. For each question, retrieve the top-k most similar chunks by cosine similarity.

**Context**: top-k chunks by embedding cosine similarity (vary k = 3, 5, 10)

### Learned Selector (Ours)

Score all chunks with the trained L1-regularized logistic regression model (`Logreg/`) and select the top-K by predicted usefulness probability.

The selector is trained on (question, chunk) pairs with weak supervision: a chunk is labeled positive if token F1 between the chunk text and the gold answer exceeds 0.15. The model uses a 130-dimensional feature vector combining:
- Lexical similarity (TF-IDF cosine, token overlap)
- Semantic similarity (frozen `all-MiniLM-L6-v2` embeddings)
- Structural signals (chunk position, log length)
- Section one-hot (19 clinical section categories)
- Question-type one-hot (6 categories)
- Section × question-type interactions (114 dimensions)

L1 regularization performs automatic feature selection, driving irrelevant weights to zero.

**Context**: top-K chunks by learned score (vary K = 1, 3, 5, 10)

## Downstream LLMs (rows of the matrix)

The same retrieval comparison is run across multiple frozen LLMs to show the learned retrieval layer generalizes across architectures.

### Phase 1: Core comparison (one fixed LLM)

Run all retrieval strategies on **o4-mini** to establish the main results table.

### Phase 2: Multi-model generalization

Extend to additional models:

|  | discharge-only | full-context | recency | BM25 | semantic RAG | **learned** |
|---|---|---|---|---|---|---|
| o4-mini | | | | | | |
| gpt-4o-mini | | | | | | |
| Llama-3-8B (HF) | | | | | | |
| Mistral-7B (HF) | | | | | | |
| Phi-3-mini (HF) | | | | | | |

Each cell contains the QA accuracy (ROUGE-L, LLM-judge, token F1) for that model × retrieval combination. The key claim is that the **learned** column outperforms all baseline columns **across all models**.

## Evaluation Metrics

### Primary: QA Accuracy

For each (question, gold_answer) pair, generate the LLM's answer given the selected context, then score:

- **ROUGE-L**: text overlap between generated and gold answer
- **LLM-as-Judge**: a larger LLM rates correctness on a 1–5 scale (using a rubric prompt)
- **Token F1 / Exact Match**: token-level overlap for factoid-style questions

### Secondary: Context Efficiency

- **Tokens Used**: count the prompt tokens for each method
- **Accuracy vs. Token Budget Curve**: plot QA accuracy as a function of context size (top-K = 1, 3, 5, 10, 25) across all retrieval methods
- **Compression Ratio**: (tokens used by method) / (tokens in full context)

### Ablations

- Weak supervision threshold: sweep F1 threshold (0.10, 0.15, 0.20, 0.30)
- Sparsity strength: vary L1 penalty (C = 0.01, 0.1, 1.0, 10.0) and measure accuracy/context trade-off
- Feature group ablation: remove temporal features, remove section features, remove interactions, compare learned vs heuristic baselines
- Event type contribution: ablate individual event types (labs only, meds only, etc.)

## Experiment Pipeline (proposed modules)

```
Evaluation/
├── PLAN.md                    # This file
├── context_builders.py        # Functions that produce LLM prompts for each baseline/method
├── llm_runner.py              # Unified LLM inference (OpenAI API + HuggingFace models)
├── scoring.py                 # ROUGE, LLM-as-judge, exact match, token F1 scoring
├── run_baselines.py           # CLI: run all baselines on test set, save results
├── run_learned.py             # CLI: run learned selector experiments
└── analysis.py                # Generate tables, plots, efficiency curves
```

### context_builders.py

One function per retrieval strategy. Each takes a patient record + question and returns a formatted prompt string:

- `build_discharge_only_prompt(record, question) -> str`
- `build_full_context_prompt(record, question) -> str`
- `build_recency_prompt(record, question, n=25) -> str`
- `build_bm25_prompt(record, question, k=5) -> str`
- `build_rag_prompt(record, question, k=5, embedder=...) -> str`
- `build_learned_prompt(record, question, selector=...) -> str`

### llm_runner.py

Unified inference wrapper supporting both API-based and local models:

- **OpenAI API models** (o4-mini, gpt-4o-mini): async client with rate limiting, retries, and response caching
- **HuggingFace models** (Llama-3-8B, Mistral-7B, Phi-3-mini): local inference via `transformers` / `vllm`, batched for throughput

All models expose the same interface: `run_llm(prompt, model_name) -> str`

### scoring.py

- `rouge_score(predicted, gold) -> dict` — ROUGE-L, ROUGE-1, ROUGE-2
- `token_f1(predicted, gold) -> float` — token-level F1
- `exact_match(predicted, gold) -> bool`
- `llm_judge_score(question, predicted, gold, model="gpt-4o") -> int` — 1–5 scale via rubric prompt

### run_baselines.py

```bash
python -m Evaluation.run_baselines --method discharge_only --model o4-mini --split verified
python -m Evaluation.run_baselines --method full_context --model o4-mini --split verified
python -m Evaluation.run_baselines --method recency --n 25 --model o4-mini --split verified
python -m Evaluation.run_baselines --method bm25 --k 5 --model o4-mini --split verified
python -m Evaluation.run_baselines --method rag --k 5 --model o4-mini --split verified
```

### run_learned.py

```bash
python -m Evaluation.run_learned --K 5 --model o4-mini --split verified
python -m Evaluation.run_learned --K 5 --model meta-llama/Meta-Llama-3-8B-Instruct --split verified
```

Outputs results to `data/results/<method>_<model>_<params>.json`.

## Execution Order

### Phase 1: Core comparison (one LLM)

1. Ensure `data/processed/patient_timelines.json` and QA pairs exist (from Preprocess + Generation pipelines)
2. Train the learned selector: `python -m Logreg.run train`
3. Implement `context_builders.py`, `llm_runner.py`, and `scoring.py`
4. Run Baseline 1 (discharge only) on o4-mini — this is the floor
5. Run Baseline 2 (full context) on o4-mini — this is the ceiling
6. Run Baselines 3–5 (recency, BM25, semantic RAG) on o4-mini
7. Run learned selector on o4-mini
8. Score all results with ROUGE-L, token F1, LLM-as-judge
9. Produce the main results table

### Phase 2: Multi-model generalization

10. Set up HuggingFace inference for open-source models (Llama-3-8B, Mistral-7B, Phi-3-mini)
11. Set up OpenAI API inference for gpt-4o-mini
12. Re-run all retrieval strategies on each additional model
13. Fill the model × retrieval matrix
14. Report per-model improvement from learned retrieval vs best heuristic baseline

### Phase 3: Analysis

15. Generate budget-efficiency curves (accuracy vs K)
16. Run ablations (feature groups, L1 penalty, supervision threshold)
17. Error analysis on failure modes
18. Produce final tables and figures for the write-up

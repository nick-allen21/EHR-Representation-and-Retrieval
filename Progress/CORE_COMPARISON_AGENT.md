## The 6 Retrieval Strategies

All strategies answer the same 1,000 questions using the same frozen LLM (o4-mini). Only the context selection differs.

| # | Strategy | What goes in the context | Implementation |
|---|---|---|---|
| 1 | **discharge_only** | Raw discharge summary, truncated to budget | Trivial truncation via tiktoken |
| 2 | **full_context** | Demographics + admission + all events + discharge summary | Serializes structured fields via `data_loader.serialize_events()` |
| 3 | **recency** | Discharge summary + N most recent events (default N=25) | Slices `events[-N:]`, serializes, concatenates with discharge |
| 4 | **bm25** | Top-K chunks ranked by BM25 score against question | Uses `rank_bm25.BM25Okapi` on chunks from `chunker.py` |
| 5 | **semantic_rag** | Top-K chunks ranked by embedding cosine similarity | Uses `all-MiniLM-L6-v2` sentence-transformer embeddings |
| 6 | **learned** | Top-K chunks from trained L1 logistic regression selector | Uses `ChunkSelector.load()` from `Logreg/selector.py` |

Strategies 4-6 all operate on the **same chunk pool** from `chunker.py` (section-based splitting with fixed-size fallback), making them directly comparable.

### Per-Difficulty Breakdown (Token F1)

| Strategy | Easy (n=239) | Medium (n=560) | Hard (n=201) |
|---|---|---|---|
| discharge_only | 0.342 | 0.367 | 0.300 |
| full_context | 0.444 | 0.421 | 0.364 |
| recency_n25 | 0.400 | 0.406 | 0.337 |
| bm25_k5 | 0.329 | 0.325 | 0.302 |
| semantic_rag_k5 | **0.493** | 0.420 | 0.356 |
| learned_k5 | 0.479 | 0.392 | 0.356 |

### Key Observations

1. **Learned selector matches full-context quality with 72% fewer tokens** (1,064 vs 3,815). This validates the core thesis — a lightweight model can identify the right evidence chunks.
2. **Semantic RAG edges out the learned selector by ~2 points** on this dev set (0.424 vs 0.406 token F1). This gap may close with more training data or better features.
3. **BM25 underperforms** — lexical matching alone is insufficient for clinical QA where paraphrasing is common.
4. **Both chunk-based methods substantially beat discharge-only** (+17-22% token F1), confirming that targeted retrieval helps even with rich discharge notes.
5. **The learned selector is strongest on easy questions** (0.479 vs semantic RAG's 0.493), suggesting it excels at direct fact lookup but may miss nuanced cross-source reasoning.
6. **All methods struggle on hard questions** (0.30-0.36 range), which require synthesizing 3+ data sources — an expected limitation under a fixed token budget.

## How the Pipeline Works

### Data Flow

```
patient_timelines.json + qa_pairs.json
        │
        ▼
  run_evaluation.py (loads & joins on subject_id, hadm_id)
        │
        ▼  for each (patient, question, gold_answer):
  context_builders.py (selects context via chosen strategy)
        │
        ▼
  llm_runner.py (sends prompt to o4-mini, caches response)
        │
        ▼
  scoring.py (token_f1 + rouge_l against gold answer)
        │
        ▼
  data/results/{strategy}.json (per-question results)
        │
        ▼
  analysis.py (summary tables, plots, JSON export)
```

### CLI Commands

```bash
# Generate upstream data
python -m Preprocess.run_pipeline --limit 200 --format json
python -m Generation.generate_qa

# Run evaluation (single strategy or all)
python -m Evaluation.run_evaluation --method discharge_only --limit 200
python -m Evaluation.run_evaluation --method all --limit 200

# Custom parameters
python -m Evaluation.run_evaluation --method bm25 --k 10 --token-budget 4096
python -m Evaluation.run_evaluation --method recency --n 50

# Analyze results
python -m Evaluation.analysis --plots
```

### Response Caching

Every LLM call is cached by hashing `SHA-256(model + messages)` to a filename in `data/results/cache/`. Re-running the same evaluation costs $0. The current cache has 5,859 entries (one per unique prompt across all 6 strategies x 1,000 questions, minus cache collisions from identical prompts).

### Reasoning Model Handling

o4-mini is a reasoning model with two quirks the runner handles:
- Uses `max_completion_tokens` instead of `max_tokens` (reasoning tokens count toward the limit)
- Does not support the `temperature` parameter
- Default budget is 4,096 completion tokens (reasoning + visible answer)

The runner auto-detects reasoning models by prefix (`o1`, `o3`, `o4`) and adjusts parameters accordingly, so swapping to `gpt-4o-mini` or any non-reasoning model works without code changes.

---

## Bugs Encountered and Fixed

1. **`max_tokens` not supported by o4-mini** — The OpenAI API returns 400 for reasoning models when `max_tokens` is used. Fixed by detecting reasoning model prefixes and switching to `max_completion_tokens`.

2. **`temperature` not supported by o4-mini** — Reasoning models ignore/reject this parameter. Fixed by conditionally omitting it for o-series models.

3. **Empty responses with small `max_completion_tokens`** — o4-mini uses internal reasoning tokens that count toward the completion budget. With `max_tokens=512`, all tokens went to reasoning, leaving nothing for the visible answer. Fixed by increasing default to 4,096.

4. **`message.content` could be `None`** — When reasoning models exhaust their token budget, `content` is `None` instead of an empty string. Fixed with `or ""` fallback.
